## 2. 生效路径与数据流

### 2.1 主线动作

`输入 → GardenGame → 克隆当前状态并创建测试 GardenWorld → move/act 合法性验证 → Motion 动画 → 正式 move/act → 保存快照 → HUD/Canvas → 通关回调`。

优点：动作先验证，动画未提交时暂停可以保留前一个稳定状态；规则大体独立于 DOM；稳定 tile ID 可以跨模块旋转、升降保持人物和物件身份。

代价：模型校验、克隆、热区与图块派生有重复工作；目前没有独立的 CommandBus、动画提交协议或渲染快照缓存。

### 2.2 三份持久化数据

| key | 数据 | 当前使用方 |
| --- | --- | --- |
| `sporelight.save.v2` | 玩家名、设置、旧关卡成绩/解锁、图鉴、旧 run | App、章节解锁、图鉴等 |
| `sporelight.garden2.v1` | 每关 runs、完成 memories、最佳 records、legacy | Garden2、菜单、地图、纪事 |
| `sporelight.cloud-gardens.v1` | runs、memories、completed、discoveries | 云庭 |

读档有异常兜底和基本结构清洗；GardenWorld 检查角色位置、物件、根路径等。撤销历史保存在运行内存，最多 400 个快照（`world.ts:44`），刷新后不恢复整段撤销历史。

旧 v2 存档仍按旧 LEVELS 清洗收集上限，因此“仅把 onComplete 里的赋值改成 max”不能彻底解决图鉴口径；必须迁移数据来源和分母。

## 5. 代码可维护性与内容生产

主要瓶颈不是代码行数，而是同一个关卡事实散落在多个地方：

- `world.ts` 初始化、动态地块、ready、act、hint 多处按 level.id 分支。
- `GardenGame.ts` 兼任输入、动作时序、UI、音效、保存、结算。
- `createApp.ts` 掌握所有场景和三套存档，改功能容易牵动导航/兼容。
- `levels.ts` 先创建数组，再通过 `out[index]` 多次修改；最终配置需要按执行顺序理解。
- CSS 多代样式串联，存在遗留负担，但本次没有实测证明具体选择器冲突。
- 多处 document 全局查询和非空断言，把 DOM 结构假设散布在控制器里。
- 密集的一行多语句降低评审可读性；格式化应与逻辑改动分开。

建议先抽取高复用能力：旋转/升降/滑动模块、携带物、角色能力、触发器、根路径、光路、水端口与目标条件。保留少量受控的特殊关卡 hook，不必提前建设完整 ECS 或庞大通用脚本语言。

关卡配置未来至少包含：稳定 id、contentVersion、地图/模块、角色能力、物件与槽位、连接端口、完成条件、观察/故事、收集、提示层级、资源包和参考解法。验证器检查重复 ID、缺失引用、非法高度/落点、收集预算、孤立区域及关键目标可达性。

## 6. 目标架构（建议，不是当前目录）

```text
src/
  app/             路由、依赖组装、会话和生命周期
  domain/          WorldState、Command、规则、Result、目标与不变量
  content/         关卡注册表、机制配置、文案、资源清单
  presentation/    Canvas、镜头、动画、HUD、菜单、可访问性
  services/        ProgressStore、SaveService、AssetManager、AudioService
  platform/        web / mobile / desktop 适配与能力查询
  legacy/          版本迁移及兼容所需的最小代码
```

建议接口边界：

| 接口 | 责任 | 禁止依赖 |
| --- | --- | --- |
| WorldEngine | apply(command)、snapshot、validate、可选 simulate | DOM、localStorage、原生 SDK |
| ProgressStore | 当前会话进度与统一 selectors | 页面自行读盘 |
| SaveRepository | load/commit/backup/migrate，报告成功或失败 | UI 内直接 JSON/setItem |
| InputRouter | 键鼠/触摸/手柄 → 统一动作 | 输入直接改 WorldState |
| RenderSnapshot | 几何、可见性、动画端点、提示状态 | 渲染帧重新执行存档迁移 |
| PlatformServices | 生命周期、震动、全屏、文件、能力查询 | 核心规则知道具体系统 |

小步迁移：先统一 selector 和 ProgressStore；再抽 SaveRepository；随后 InputRouter/生命周期；再拆机制。每步保持 12+3 关可玩和存档迁移兼容，避免以目录搬家替代实际问题修复。

## 7. 存档改造细则

建议单一 envelope：`schemaVersion / contentVersion / revision / savedAt / profile / settings / campaign / cloud / completedMemories`。版本号必须服务于迁移，不复用 package 版本作为唯一依据。

1. 首次加载读取新档；没有新档时读取当前三套存档、校验、合并并保留原始备份，同时兼容公共存档 `sporelight.save.v1` 的历史回退来源。
2. 主线完成记录成为解锁和收藏的事实来源；地图、图鉴、纪事不再分别推算旧值。
3. commit 写入候选并校验，再切换有效代次；IndexedDB 可使用事务，原生文件使用平台支持的安全替换方式。
4. 保存失败保留内存状态和可重试队列，避免返回菜单时读盘覆盖本次进度。
5. 损坏时恢复最后有效备份，并告知恢复到了哪里；不要默默覆盖坏档证据。
6. 迁移旧完成记录但没有修复快照时，区分“历史通关”和“当前可回看快照”。
7. 导入/导出先校验版本和数据上限，导入前留备份；跨端云同步先采用显式冲突选择，不盲目按设备时钟覆盖。

## 8. 已有测试价值与缺口

本次 135/135 规则测试通过，覆盖旧规则/格子、动作、图鉴、云庭和 Garden2；Garden2 有每关设计解法逐步保存/恢复、全部 56 收集可得、根线回收、载物旋转、真实光路、留影与最终动态条件测试。

需要补的关键回归：

- 应用级：首次通关、重玩提分、解锁、图鉴、回看、保存失败必须一致。
- 异常恢复：坏 JSON、旧档、缺字段、部分写失败、容量不足、刷新/杀进程、版本升级。
- 输入：真实触摸、取消/切屏、手柄导航、键鼠切换，不重复提交同一动作。
