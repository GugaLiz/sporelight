# 首关原生深度与移动表现优化记录

日期：2026-11-06。当前实施范围为1-1；其它11关继续已有表现分支，后续推广须单独验收。

本文记录用户拒绝压短楼梯方案之后的处理。原始图片、谜题规则、种子预算、地块ID与高度、路线邻接、通关条件、输入动作提交及存档仍由现有代码负责。本轮把首关世界画面放入原生3D深度场景，并继续使用原`GardenPaint`绘制及素材，不是重新制作整套3D美术。

这里的连续移动仍是离散规则图上的输入、预览与插值；没有接入`CharacterBody3D`、`move_and_slide()`或新的物理碰撞驱动。表现层支撑查询不能自行创造通路。

## 2. 原生深度场景与原画保留方式

当前`GardenView._draw()`仅在`level.id == "1-1"`时启用`GardenDepthStage`：背景和HUD仍按原界面绘制，世界画面进入透明`SubViewport/World3D`，输出纹理再合成回原界面。

`GardenPaint`继续生成原来的图片、墙砖UV、面、多段线与渐变。`GardenDepthPaintTarget`接收这些最终屏幕坐标，根据对象所属面反解成3D顶点：

| 面类型 | 真实空间定义 | 典型对象 |
| --- | --- | --- |
| `ground(h)` | 固定高度的水平面 | 岛顶、踏面、顶部水流 |
| `x(x)` / `z(z)` | 固定X或Z的竖直面 | 外墙、阶梯立面、槽内壁、水幕 |
| `ramp(surface)` | 由低高端点和纵向范围定义的斜面 | 后排嵌入式石坡 |
| `billboard(anchor)` | 以世界脚锚定位、横轴平行相机right、竖轴为世界UP的竖直贴片 | 人物、伙伴、花草、部分道具 |

因此原人物图片仍朝向屏幕，但不再位于一个能跨过所有平台的全局2D图层。深度缓冲根据真实位置比较岛面、人物及前景；原画里已经画出的光影不会再被一组新灯光重复照亮。

原投影继续为：

```text
raw_x = (x - z) * 35
raw_y = (x + z) * 17.5 - h * 48
world3d = (x, h * 1.1197668465, z)
pixels_per_world_unit = 49.4974746831 * scale
```

`DepthStage.setup_size()`使用45°方位角、30°俯角的正交相机，以现有`origin/scale`恢复原构图。相机随原逻辑锚点插值，不能跟着每一级抬脚上下颠。正交相机保持远近对象尺寸一致，适合保留本项目的等距图像关系；相关API与`unproject_position()`说明见[Godot Camera3D官方文档](https://docs.godotengine.org/en/stable/classes/class_camera3d.html)。上面的具体比例是本项目投影校准结果，不是引擎默认值。

## 3. 长梯、入口槽和石坡不是同一件事

### 3.1 右根桥：八级长梯

右桥`g:root:1:0/h0 ↔ f:2:0/h1`恢复舒适的`.1… .9`纵向范围，半宽`.29`。总高差仍为1，分为8级，每级`.125`世界高度，即6个设计像素；每级进深`.1`格。没有改变种子所创建的逻辑根格，也没有把缺口缩短。

阶梯后半段进入高台的部分不再与完整顶面重叠。`StairSurface.slot_top()`和`GardenLandscape`按建筑描述在高台局部减去入口槽，去除恰好挡在通行位置的上部立面条带，并补齐内侧墙。主体岛轮廓、槽下方墙体和其余墙砖继续保留。

当前入口参数集中在`stair_surface.gd`：槽从`u=.5`进入高格，远侧`v=-.34`，近侧至当前地块前沿`v=.5`，末端由该连接`run_end`决定。这是首关当前相机下的建筑剖面，不是面向所有关卡的通用开口宽度。

建筑入口是固定实体预留；右根桥未长出时，虚拟根端仅用于这份建筑几何描述，不会进入规则地块、寻路、连接动画或人物接触。实际桥板及其连接仍由真实播种状态决定，并沿文档30的透明度过渡。

### 3.2 连续支撑轨与可见踏面的真实区别

这版没有再让身体在短短205ms的一格移动中执行8次突兀的竖直跳动。人物查询`contact()`的连续支撑轨：右桥`rail_start=0、rail_end=.8`，高度在两端之间连续变化；可见的8个踏面仍为水平阶面。

**连续轨不是每一时刻都踩实水平踏面。** 它是小台阶的表现支撑近似。`rail_h`报告轨高，`support_h/ground`报告实际阶面，`clearance/penetration`分别报告离地及穿入，不能把二者混成一个“误差0”的数据。对于这个6px阶高的长梯，设计离地量应受单级阶高约束，并在完整人物画面里确认不会显得悬浮。

规则允许的其它首关一步高差连接通过`connection()`生成描述；一般阶梯当前使用`.275… .875`的8级实体及`.2… .8`的连续轨。它们仍需与右桥一样检验实际落脚和完整动作，不能只看共享函数存在就认定自然。

### 3.3 两处已删除后排楼梯：石坡连接

`f:2:0↔f:2:-1`和`f:3:0↔f:3:-1`不恢复用户已删除的楼梯外观。原有规则邻接仍存在，因此采用嵌入式石坡表达该高差连接；`style="ramp"`、纵向`.2… .8`。

石坡是真实斜面，人物轨高与坡面高度一致；它与“水平踏面＋连续轨近似”的阶梯不同。`DepthPaintTarget.ramp()`对四个方向统一反解斜面，`Landscape`沿用原stone/moss素材，而非新增一块无材质的灰色模型。坡槽同样采用真实顶面开口、局部立面及内壁，不能把坡面埋入原完整高台。

## 4. 首关恒定站位与真实脚锚

`actor_ground_point()`在1-1的整段游玩中采用同一世界坐标约定：

| 角色 | 相对逻辑格心的恒定 `(x,z)` 偏移 |
| --- | --- |
| 露薇 | `(-.02,-.18)` |
| 伙伴 | `(-.18,.18)` |

这不是给每次动画另加一套临时编队。静止、起步、移动、回头、上岸、离开落脚区、`p=1`提交和`clear_motion()`继续同一站位；低动态即时提交、撤销和读档也从状态重建同一个锚点。

人物高度以当前真实连接的支撑查询为准，跳跃高度另外叠加。地面脚环使用地面接触基线；人物、携带物、保护框和屏幕身体脚点共用实际身体锚。原人物素材的`+7px/+4px`等绘图基准不再注入世界`x/z`，避免2D看似对齐却让3D深度锚漂进另一格。

本项目仍使用既有离散命令与持续方向输入；按住方向的连续行走保留，松键停止与动作提交仍由原应用层负责。连续轨是表现层支持面，不会越过不存在的桥、跨越规则禁止的两级高差，也不是物理引擎自动寻路。

## 5. 深度正确之后仍需要美术适配

先行完整路线截图里，主角到达`f:2:0`时，110宽花床的原PNG连同宽底座覆盖了人物大部分下身；初始站位和后排转向时，两个人物也曾堆叠得难辨。这个结果虽然可以是正确深度遮挡，仍不适合交付。

当前仅将1-1的`core`图片显示宽度110改为86，原PNG、原位置、逻辑格、点击目标和修复条件不变。其它关卡110宽与3-4的150宽不受这一条件影响。这个调整是对单张带底座图片在70宽格子中的实际占地做适配，不能推广成全场景统一缩小。

原生深度不会自动把“正确遮挡”变成“舒服画面”。继续检查人物脸、身体、脚与目标物的关系；确需提示时，应优先限制在当前操控人物被已知植物类软遮挡物挡住的范围，不能穿透石墙显示未发现路径。本轮没有宣称已经实现完整人物透视提示系统。

瀑布也需要指定真实平面：顶部水流在`ground(source.h+.002)`，下落水幕在立面外侧`z=lip.z+.003`。若把整段水绘在格心billboard里，实体墙会按真实深度把水幕挡住；这应通过水体所属面修正，不能把全部水和人物置顶。

## 6. 材质、透明与同面图案层次

`DepthStage`使用无光照材质、线性tonemap并关闭额外雾与glow，以保留原贴图和顶点颜色。Godot官方说明Unshaded不再计算灯光；透明Depth Pre-Pass先处理不透明部分，半透明区域仍可能存在混合与排序局限。因此本轮选用它来保留PNG软边和渐变，不意味着引擎自动消除所有透明问题。[官方材质与透明模式说明](https://docs.godotengine.org/en/stable/tutorials/3d/standard_material_3d.html)

完全透明的图片区域不能成为一张挡住后方场景的实心矩形。永久投影测试只验证源alpha和材质属性；独立GPU遮挡测试才检查实际片元行为，两种证据不能互相替代。

原base→texture→gradient→line仍需保持同面叠绘次序。当前只使用每次`1e-5`、上限256层的微小视线方向几何偏移，不改变屏幕投影，也不设置能压过真实深度的`render_priority`。它只解决几乎共面的贴图层次，不用于把身体穿过建筑。

## 7. 静态网格缓存与性能边界

最初原生深度候选每帧重新提交全部地形，debug单机移动采样p95约25ms。该数字只是当时的调试包测量，不能与后续正式包混成同一组性能结论。

当前把`floor/steps/ramp/prop`按稳定对象描述分组，以`hash([level.id, stable_objects])`决定是否重建：

- `begin_static(signature)`未变化时跳过绘制记录和网格提交；`end_static()`提交改变后的静态组。
- 动态人物、mark、收藏和水幕等继续走`begin_frame()/end_frame()`。
- 缓存顶点是真实世界坐标，单纯相机移动、窗口尺寸、origin或scale改变不应触发静态重建；结构、可见性、拓扑或透明度改变必须体现在签名中。
- 静态和动态分别持有有限的MeshInstance池，共用材质缓存；离开场景可禁用stage，明确失效时可调用`invalidate_static()`。
- `last_frame`分别报告动态和`staticCalls/staticTriangles/staticBatches/staticInstances`，便于判断是否只是把大量重建藏进另一组统计。

ArrayMesh使用顶点、颜色、UV和索引数组提交几何；这是本项目保留原Paint输出的适配方式，见[Godot ArrayMesh官方教程](https://docs.godotengine.org/en/stable/tutorials/3d/procedural_geometry/arraymesh.html)。按纹理/材质合批和静态重用是当前实现选择，不代表已经对所有关卡或持续生成新纹理的情况建立无界缓存治理。

Godot官方也指出透明对象有混合及排序成本，不能把所有面都当成免费半透明贴片；本轮应先完成同源码、独占GPU的正式包前后采样，再考虑进一步实例化或减少透明叠层。[官方3D性能说明](https://docs.godotengine.org/en/stable/tutorials/performance/optimizing_3d_performance.html)

## 9. 可复用处理配方与诊断决策

| 看到的现象 | 先查什么 | 正确处理方向 | 不采用的捷径 |
| --- | --- | --- | --- |
| 播种第一帧整块墙消失 | 生成根格是否参与主体结构遮面 | 固定来源身份、真实前后连接集合、只让动态桥渐显 | 用alpha阈值推迟删墙 |
| 脚点数据正确但小腿被切 | 踏面与完整台面是否重叠；绘图对象实际在哪个3D面 | 建立真实入口槽/内壁，共用支撑描述 | 抬高所有人物或全局置顶 |
| 梯子变竖直、身体每阶抽动 | 进深/总高差与动作时长 | 保留长进深，细分小阶，明确连续轨近似及离地上限 | 压短梯程后用测试数量证明舒服 |
| 到站或清动画横漂 | 逻辑格心、队形、素材pivot是否混用 | 同一世界锚与恒定站位贯穿动作生命周期 | `p=1`后临时换坐标体系 |
| 原生深度下人物只剩帽子 | 道具PNG包含的底座、实际尺寸和人物站位 | 针对该关适配原图占地并看完整场景 | 认定“深度正确所以无需再改” |
| 生长时墙砖轻微跳色 | 裁切前后是否重新算/钳制gradient UV、是否改变三角网格 | 保留原三角形UV平面，固定建筑几何 | 只检查一小块ROI而忽略整幅图 |
| 水幕消失在墙后 | 水是否仍在格心billboard或墙内 | 顶部ground、下落facade外plane | 把全部特效关闭depth |
| 行走帧时变高 | 每帧提交数量、静态网格签名与透明叠层 | 静态重用，动态局部更新，再做同源测量 | 拿debug与release不同包的p95直接相减 |
| 想推广到下一关 | 动态结构、机关、实际路径和相机条件 | per-level明确开关，逐关验证真实路径/遮挡/过渡/性能 | 只因公共helper存在就全部开启 |

实际复用顺序：先冻结规则状态与参考路线；再写建筑实体和支撑描述；校准投影；让原画进入明确的真实面；检查完整人物连续动作；最后核对输入/存档和性能。规则正确、几何正确、像素正确和游玩舒适是四类验收，缺一类都不能用其它类代替。

## 11. 后续两轮实图修正

### 11.1 材质必须按实际alpha分类

原生初版把所有纹理都送入透明通道，完全不透明的墙砖JPG也参与透明颜色排序，导致本来位于墙外的半透明水幕被后绘制的墙颜色覆盖。水幕记录器证明40个三角形、42个顶点均在`z=.503`，并非仍在墙内。

第一版分类修复只信`Texture2D.has_alpha()`，在本机压缩PNG上误判为false，实图出现人物和花草的黑白不透明矩形。该失败图保留在`route-readable/`，不能作为最终效果。最终对静态纹理首次读取源`Image.detect_alpha()`并缓存；JPG及真正全不透明RGBA进入opaque pass，原角色/花草PNG与渐变保持透明；动态Viewport纹理始终透明且不读回GPU。

水幕仅用`transparent_priority=1`让混合晚于墙面透明涂层；默认对象为0，不透明对象忽略该值，真实depth仍开着。这是混合阶段调度，不是把水幕画在一切前面。最终正常图里水幕、原PNG透明边缘均恢复。

### 11.2 植物可读性与标注避让

仅缩小花床仍会在落岸后挡住主角。本轮加了局部软遮挡策略：只有1-1已经可见的core花床，按当前操控角色的世界距离、前后关系及高差平滑淡化，最低alpha为`.38`；远离、走到前方或进入不同高度后恢复。solid岛墙、未接通缺口、其它道具和其它11关不采用此策略。查询无副作用，不生成道路或交互。

这是一项明确的视觉设计变化：当前整张花床PNG连底座一起淡化，依据是几何接近，不是逐像素遮挡面积或物理raycast。它有幽灵感风险，也可能更早露出花床后已存在的空间；不能声称原来的信息揭示节奏完全不变。后续同类场景应在“只调原图占地、拆底座为实体、局部轮廓提示、软植物淡化”中按谜题设计选择，禁止把整座石墙一起透明。

根台和花床标签优先保持原位置，若压到主角保护区则移到保护区边缘；确实无位置时省略装饰标签，HUD交互仍在。最初固定64/80px候选全部碰到保护框时会退回遮脸位置，最终改为从保护区边界计算候选，避免这种失败回退。
