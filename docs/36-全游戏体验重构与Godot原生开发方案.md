# 全游戏体验重构与 Godot 原生开发方案

日期：2026-11-06
状态：设计方案已获授权实施；本轮基础重构的实际范围、入口与验收结果见 [文档 37](37-原生2.5D全游戏重构与验收.md)。本文保留原始设计意图，不表示每项后续美术制作和设备认证都已完成。
范围：12 个主线关卡、3 个云庭关卡，以及操作、角色、场景、镜头、界面、声音、存档与完整旅程。
最初分析阶段仅交付方案；用户随后授权多 agent 实施，实际改动和验证由文档 37 与 agentchanges 记录。

## 1. 总体方向与边界

建议整体重构体验层与场景制作方式。保留种子创造道路、空间变化、双角色协作、光水影与时序组合等核心谜题，保留角色、植物、建筑、纹理和艺术风格；重新设计操作语法、空间布置、人物动作、镜头、界面与反馈。

推荐采用固定正交视角的原生 2.5D：真实 3D 地形和碰撞承载空间，现有图片角色与植物保留艺术身份，Godot 原生场景、动画、输入、UI 和音频承担基础设施。

本方案取代文档 25 中按旧像素、旧操作序列与旧投影保真的体验约束。规则安全、种子预算、解谜依赖与存档可靠性继续保留。文档 30—35 中有效的地形稳定、接触、导航语义等原则纳入公共规范，不继续依赖 1-1 特例。

“使用引擎”不等于没有玩法代码。引擎提供运动、碰撞、动画播放、空间变换与布局；种子能否收回、光是否到达、两个角色是否满足机关条件仍由规则维护。现有规则值得复用，适配连续运动时部分事务接口需要调整。

### 保留合同

| 必须保留 | 可自由重做 |
|---|---|
| 有限芽节、连续生长、回收、分支和可选探索 | 旧地形尺寸、坐标、机关间距离与关卡分段 |
| 未种植或未开放的道路不能通过 | 输入方式、按键组合、交互距离与 UI |
| 旋转、升降、移动改变连接与承载 | 镜头、演出、动作节奏与场景布置 |
| 两位角色的能力、站位和合作依赖 | 素材切分、统一规格、图集与派生渲染 |
| 光、水、影与顺序满足当下真实条件 | 提示层级、任务呈现、奖励和章节入口 |
| 脚下通路不能非法收回，关键物品不能丢失 | 已解区段的往返组织与观赏路线 |
| 撤销、保存、继续和回看可靠 | 旧参考解的精确按键数和移动序列 |

每次布局改变先检查依赖图、替代解与非法捷径，尤其是低拱、压板、镜叶射程和水路。不能只凭截图重新排布。

## 2. 当前问题与证据

依据：主线与云庭规则、Godot 工程、旧版入口、已有桌面/横竖屏 QA 画面，以及三路并行只读审查。此次没有开展新的无引导玩家试玩、浏览器操作或目标设备性能实测。

| 代码/画面事实 | 体验判断 | 调整方向 |
|---|---|---|
| 有限根路、旋转/升降/移动、角色能力、光、水、影和顺序机制已经存在 | 主要短板不在机关数量，而在操作和表达 | 优先完善体验，暂不扩充机关门类 |
| main.gd 的 _primary 优先取 mirror_guidance.action，再选首个命令 | 主动作可能替玩家决定解法，按键前意图不明确 | 动作来自当前目标，具体方向由玩家选择 |
| journey_view.gd 常驻下一步读取 world.hint()，部分关卡直接给方向/步骤 | 默认界面提前回答谜题 | 常驻目标讲意图，解法进入主动请求的分级提示 |
| 任务卡、右命令卡、工具排、方向盘、全景、消息同时出现 | 玩家像在管理控制台，世界被挤到剩余区域 | 世界承担主要操作，HUD 退到辅助位置 |
| 390×844 QA 中卡片覆盖高台，568×320 中世界区域狭窄 | 响应布局主要在容纳控件 | 先保证角色、目标和落脚区，再安放控件 |
| garden_view.gd 只有 1-1 开启 depth_enabled | 其他 11 关仍用旧二维排序，体验不统一 | 所有关卡统一空间、脚点、深度与朝向 |
| main.tscn 只有根节点，大量内容由代码构造 | 编辑器与复用场景优势尚未充分使用 | PackedScene、Resource 和可视化锚点制作关卡 |
| 运动、接触和动作依赖定时插值、帧号和公式 | 不同动作缺少重量、触点与因果节奏 | 正式运动组件和动作片段 |
| 多数非移动动作统一为 0.78 秒 | 提物、播种、转整座庭院的等待感相近 | 每种行为独立设计预备、接触、结果、收势 |
| 走路素材的方向、循环长度、脚轴和比例不一致 | 调平滑曲线无法根治滑步与转向突兀 | 先统一资产规格 |
| 已使用 Camera3D、ArrayMesh、Control 和音频节点 | 引擎已经接入，主体仍有旧表现结构 | 替换 Canvas 到 3D 转译及手工空间管理 |
| 动态深度提交会创建 ArrayMesh | 存在值得测量的资源更新成本，尚未证明是瓶颈 | 保持网格/材质稳定，用剖析决定优化 |

关键位置：godot/application/main.gd、application/journey_view.gd、core/garden_world.gd、presentation/world/garden_view.gd、presentation/actors/character_motion.gd、ui/garden_hud.gd。

参考解中，1-3 约 10 条命令，1-4 约 50 条；3-4 约 96 条，其中约 81 条是移动。它们只代表一份参考解，不是难度评分或实测时长，但提示应专门检查往返与角色调度。

现有测试证明部分功能、规则和回归正确；不能将其解释为已经舒适、流畅或有趣。

## 4. 玩家体验与统一操作

目标链条：

观察未复苏的花园 → 产生空间假设 → 靠近对象 → 明确选择 → 动作执行 → 世界回应 → 尝试/撤销 → 找到连接 → 花园复苏。

优先解决看清、移动、操作和因果，再增加装饰表现。辨识度集中在用植物改变通路、与伙伴安排空间。

### 4.1 连续行走

- 按住键盘方向连续移动，途中可以转向，不要求每按一次走一格，不在格子中心强制停顿。
- 输入按屏幕建立直觉映射；窄路可轻度贴路。斜向速度统一，坡度不参与角色方向帧选择。
- 起步及时，收步短而明确；身体感不能造成松手滑行和谜题定位困难。
- 普通收势不锁住下一次行走输入；有意义的提物/播种动作才短暂限制状态。
- 点地移动与伙伴跟随只沿当前已开放、规则允许的路线；不会代替玩家种路或操作机关。
- 跳跃和滚动退出常驻工具排，保留快捷动作/情境表现，不绕过断路和角色能力。

默认建议：WASD/方向键移动，E 交互，T 换手，Z 撤销，H 请求提示，Esc 暂停。手柄使用左摇杆和少量情境键；触屏以点地、点对象为主，虚拟摇杆可选。

### 4.2 主动作与根路

鼠标悬停、朝向、距离和视线决定稳定目标；有范围迟滞，避免两个物件间闪换。对象旁显示“提起镜叶/转动庭院”等动词。多个动作时显示局部选择，不常驻完整命令表。

主动作不得读取解答来挑选操作。帮助与交互分离。

根路流程：接近根台 → 唤醒局部生长 → 玩家选择当前根尖合法方向 → 预览一节成本/落点 → 确认生长 → 成为可走实体。

只显示当前已知选择，不铺出未来正确路线。余量由根台/种子袋和小数字表达；回收是同一操作内的明确次级动作。角色、物品或依赖占用时指出具体阻挡。单芽预算、主路/支路选择和隐藏发现保留。

### 4.3 机关、伙伴和撤销

旋转、水阀和升降有可见把手/档位；鼠标拖动或键盘选择后吸附到合法状态。提物需要触碰、携带锚点和合法槽位预览。

伙伴的跟随、等待、保持机关、携带和会合能从姿态和位置读出。换手不等于放弃正在保持的工作；跟随 AI 不自动完成机关。

连续行走以一次移动意图分组撤销，机关操作独立记录。角色站位仍完整可逆。可在旅程页明确提供回到最近机关操作前，不能悄悄跳过重要状态。

错误在对象上表达：边缘止步、缺一芽、低拱与伙伴图标、被墙截断的光。文字补充具体原因，避免每碰一次边界都弹长句。

### 4.4 提示与奖励

提示三级：观察可见现象 → 提醒规则关系 → 主动再次请求才给具体步骤。常驻目标是一句意图；卡住时先邀请打开帮助，不自动展示解法。

完成先发生在世界里：花、水、光、声音和伙伴共同回应，再出现轻量“下一片/留下看看”。微光体现可选发现；末关自动礼物应表达复苏里程碑。

观察、坐一会儿需要对应视线/姿态/环境变化，保持可选且随时离开。

## 5. 镜头、遮挡与屏幕适配

固定三分之四正交镜头，使用稳定边界、跟随死区、有限前瞻和作者设置兴趣点。取景边界来自资源，不随根路长出或装饰出现重新缩放全图。

支持有限缩放、拖看、复位。远处连锁变化短暂提示后恢复控制。有限窥看需核验素材与谜题；不默认自由旋转镜头。

| 遮挡类型 | 处理规则 |
|---|---|
| 尚未发现、承担谜题作用的信息 | 发现条件控制，不因通用透明规则泄漏 |
| 已发现但被建筑遮住的内容 | 作者指定局部切面、窗口、轮廓或窥看 |
| 花草/栏杆等装饰遮住角色 | 相机到角色检测，局部淡化或裁切，离开恢复 |

原生深度承担基础前后关系。透明图片仍需剪裁/深度预通道/受控透明分类，不能靠角色永远置顶修复。[SpriteBase3D 官方说明](https://docs.godotengine.org/en/stable/classes/class_spritebase3d.html)

楼梯的踏面、平滑坡面碰撞、上下接口与脚点来自同一空间定义；平台边缘真有开口，不能在完整方块上再叠斜梯。

| 屏幕 | 适配 |
|---|---|
| 大屏/超宽屏 | 保持角色合理尺寸，增加环境与观察范围，HUD 不无限放大 |
| 笔记本/小窗口 | 紧凑 HUD，提示避开角色/目标，允许跟随 |
| 手机竖屏 | 纵向构图和拖看，工具抽屉，独立触控安全区 |
| 手机横屏/低高度 | 压缩上下常驻信息，避免多排大型卡片 |
| 大字体/减少动态 | 文本重排、焦点可见，保留方向和操作节奏，减少摇摆/闪光/镜头运动 |

桌面常驻仅保留角色/携物或芽节、小撤销、暂停；目标短暂出现后收起。PC 隐藏方向盘。触屏保证点击尺寸，重叠目标有选择条，不能仅靠颜色表达条件。

## 6. 素材、动作与声音制作

保留原图归档，派生资产有来源记录。“素材相同”保留身份、造型、纹理和风格，允许切分、清理、统一规格与重新渲染使用方式。

角色规范包括世界身高、比例、pixels-per-unit、固定脚轴、前/侧/背方向、携带点、阴影和动作命名。先整理行走帧的视角、周期、步长，再做站立、起停、转身、拿取、携带、播种、等待、保持机关与完成。

脚轴固定，不按每帧透明像素最低点贴地。缺帧需从原设计补绘/派生，引擎不会自动生成正确动作或缺失视角。

图片动作使用 AnimatedSprite3D/SpriteFrames，AnimationPlayer 管理动作、音频和事件，确有组合复杂性再使用 AnimationTree。动画只影响 Visual 子树，motor 写角色根位置；不要用两个半透明角色重影来掩盖坏帧。[AnimationTree 官方说明](https://docs.godotengine.org/en/stable/tutorials/animation/animation_tree.html)

地形顶面、墙面、边缘、根路和装饰分开。完整等角建筑图不能再整体贴在 3D 盒子上，避免重复透视。植物按前/后层、贴地/竖立、可淡化/保密分类。主角和伙伴使用统一尺度、受光、脚点标准。

每个交互具备意图、确认、执行、结果四阶段。手接触、种子落下、把手转动有明确触点；不同物体有不同节奏。跳过演出仍得到同一最终状态，不重复提交。

Music、Ambience、World SFX、UI 分总线，脚步与触点事件同步，根须、石台、水位、镜叶和伙伴各有语义。优先整理现有声音，缺口单列制作。背景艺术丰富时降低可玩区周边竞争，风格与清晰度共同校准。

## 7. Godot 原生架构与规则适配

### 7.1 方案选择

| 路线 | 优点 | 代价与结论 |
|---|---|---|
| 原生 2D 与分层精灵 | 图片复用直接，渲染简单 | 高差、斜梯和旋转承载仍需专门处理；本游戏空间机关多，不作为首选 |
| 原生 2.5D：真实地形 + 图片角色/植物 | 空间、碰撞一致，保留现有艺术素材 | 需整理几何与素材；推荐 |
| 全 3D 角色与自由镜头 | 完整视角与骨骼表现空间 | 新资产量显著增加，当前素材缺面；本轮不默认采用 |

原生系统提供成熟能力，流畅度仍取决于制作、配置和测量，不能宣称换节点即可自动修复所有问题。

### 7.2 引擎与游戏的分工

| 工作 | 引擎能力 | 保留的游戏代码 |
|---|---|---|
| 地面/墙/坡道 | MeshInstance3D、StaticBody3D、CollisionShape3D | 模块连接与通路状态 |
| 人物 | CharacterBody3D、move_and_slide、坡面检测/吸附 | 输入意图、能力、通行许可 |
| 图片与动作 | Sprite3D/AnimatedSprite3D、AnimationPlayer，必要时 AnimationTree | 动作状态与规则事件适配 |
| 移动/旋转/升降 | AnimatableBody3D、物理同步动画 | 合法档位、乘客和连接 |
| 目标选择 | Area3D、射线、层与掩码 | 目标优先级、动作与阻挡原因 |
| 点击走路/跟随 | 合法图路径，必要时 NavigationAgent/Link | 路径权限与特殊通过过程 |
| 镜头/遮挡 | Camera3D、射线、材质、配置区域 | 发现规则、切面和镜头意图 |
| 页面/UI | Control、Containers、Theme、焦点和输入消费 | 页面来源、保存、继续与回看 |
| 声音 | AudioStreamPlayer3D/2D、总线 | 环境恢复阶段与事件映射 |
| 关卡制作 | PackedScene、自定义 Resource、编辑器锚点 | 稳定 ID、依赖与验证 |

CharacterBody3D 提供墙、坡面等运动接口，运动策略仍由脚本控制。[官方说明](https://docs.godotengine.org/en/stable/classes/class_characterbody3d.html)
AnimatableBody3D 适合平台和门等运动物体，需遵守物理同步方式。[官方说明](https://docs.godotengine.org/en/stable/classes/class_animatablebody3d.html)
NavigationLink 只提供寻路连接，不会自动执行梯子、跳跃或登平台。[官方说明](https://docs.godotengine.org/en/stable/tutorials/navigation/navigation_using_navigationlinks.html)

### 7.3 场景与资源

建议拆分：

- App：页面、服务、输入。
- GameStage：关卡、镜头、音景、HUD。
- Character：碰撞根、motor、Visual、交互检测、携带锚点。
- Ground / Ramp / RootBridge：可视面、碰撞、支撑 ID、连接端口。
- RotateGarden / Lift / MovingGarden：承载空间、停靠口、动作。
- SeedBed / Lever / Plate / MirrorSlot / WaterNode / ShadowSource：统一合同下的具体机关。
- Home / ChapterMap / Pause / Settings / Journal / Gallery / Completion：独立 UI 场景。

数据资源包含 LevelDefinition、SurfaceDefinition、InteractionDefinition、ActorPresentation、PresentationPreset、HintDefinition、AssetManifest。分别记录关卡规则/场景、支撑连接、交互条件、角色规格、表现预设、三级帮助、资产来源。

Resource 存数据，场景节点提供行为；新关卡优先组合实例和配置，减少共享 renderer 中的 level_id 分支。[Resources 官方说明](https://docs.godotengine.org/en/stable/tutorials/scripting/resources.html)

先用 Godot 编辑器和少量校验完成代表关卡，不先开发庞大自制编辑器或动画语言。确实重复的工作再提取组件。

### 7.4 连续运动与原规则的适配合同

现有 GardenWorld.move() 同时改主角格子、自动推进伙伴、解除保持、触发收集并记历史。不能直接让主角接上物理、保留伙伴自动跳格，否则规则位置会领先画面。

原则：规则记录支撑身份，motor 记录连续姿态，两者共同组成有效状态。它们不同时维护世界坐标，不每帧互相纠正。

| 数据 | 职责 |
|---|---|
| RuleState | 支撑 ID、道路/机关、物品、种子、收集与完成条件 |
| MotorPose | 支撑局部连续位置、朝向、速度 |
| TraversalEdge/Portal | 起终点、真实连接面、允许角色、开放条件 |
| RuntimeOccupancy | 胶囊实际覆盖、跨边预约、平台乘员 |
| RuntimeMemento | 规则快照、双方稳定姿态、物品与机关姿态 |

具体合同：

1. 支撑 ID 稳定，平台使用模块 ID + 局部单元 ID。坡道可作为连接面。不能寻找最近格子决定人物在哪层，上下重叠时必须依据碰撞、当前支撑和合法边。
2. 单元内连续走动不提交规则，不吸到中心。跨边前扫掠检查权限并预约支撑；实际穿越阈值后才提交显式 actor_id 位移。高速一帧越多边也逐条核验。
3. 跨坡道可以停下和反向，尚未完全离开时仍占用源、目标和连接面；回收通路同时检查逻辑占位、胶囊和物品。
4. 键盘、点击与伙伴跟随都给同一个 motor 意图。跟随只选目标，伙伴实际到达后通过相同事务提交；拆掉主角移动自动改伙伴位置的耦合。
5. 正常运行只有 motor 写角色根变换；动画写 Visual。撤销/读档/重生才允许生命周期内一次性恢复根位置。
6. 平台保存乘员局部位置，承载只用一条路径，避免父变换、平台速度和手工补偿重复施加。
7. 模块区分操作目标、运动过渡、几何到位。运动中关闭受影响上下口，互斥冲突操作；外部通行和完成条件不能读取尚未到位的结果。
8. 根路具 preview/growing/ready/retracting 阶段。承载面到位的物理更新点同步开放碰撞和许可；回收先检查占用、封闭新入口，再退场。
9. Portal 守卫覆盖斜向切角、跳跃、高处落下和角色体型。NavMesh 不拥有通路许可。跳跃若可能绕谜题，只能走批准的 JumpTraversal。
10. 交互同时检查真实距离、支撑与稳定状态，防止站在梯子上远程操作另一层机关。
11. 保留预演、版本核验、一次提交的思想；实际规则/碰撞在统一物理边界协调，不拿几秒前预演结果盲目提交。
12. 动画通知事务协调器；协调器保证提交一次。跳过、撤销、返回首页和加载统一处理过渡，不能依赖某个回调恰好触发。

### 7.5 保存与撤销

RuntimeMemento 同时保存两名角色、支撑局部位置、机关、物品和规则；连续移动按意图分组，机关事务独立。

恢复时暂停输入，取消旧动作/回调并更新过渡代号，恢复稳定几何与碰撞，再一次性恢复角色，清零速度后继续。不能规则先回退、身体靠逐帧纠偏追赶。

新存档增加版本和局部姿态。旧档格子映射到同一合法支撑的安全锚点，不能传送到最近的另一层平台。布局版本变化需显式映射或保留完成/发现记录并明确说明进行中关卡的恢复策略。

持久化采用稳定状态；机关短过渡中的保存请求由会话协调，明确等待到位或恢复已提交检查点。返回首页、强制重载和撤销均验证，不丢失已提交种植。

## 8. 可复用优化规则与记录

每个模块交付适用场景、参数、预设、边界条件、最小样例和修复记录。修复先映射公共规则，关卡差异放资源配置。

| 规则 | 核心内容 | 验证 |
|---|---|---|
| S01 空间一致 | 世界比例、支撑、端口、坡道、脚点同源 | 上下坡和平台接口连续 |
| S02 单一运动执行者 | motor 写根，动作写 Visual | 起停、承载、撤销无抢位置 |
| S03 拓扑稳定 | 只更新受影响模块 | 种路时墙、纹理、镜头不跳 |
| S04 语义遮挡 | 未知、结构、装饰分别标记 | 人物可读，秘密不泄漏 |
| S05 目标明确 | 稳定对象和动词，不读取解答 | 重叠、移动按键不误操作 |
| S06 原子结果 | 规则、碰撞、表现一致 | 快点、跳过、返回无双提交 |
| S07 资产规格 | 脚轴、尺寸、方向、循环、导入统一 | 所有方向接地，无滑步 |
| S08 屏幕合同 | 角色、目标、落脚区优先 | 横竖屏、小窗、大字体、触摸 |
| S09 提示分层 | 帮助与操作分离 | 默认无解法，替代解保留 |
| S10 谜题不变量 | 布局前后检查依赖与捷径 | 种路、能力、当下因果都成立 |

后续遇到类似问题先复用预设；确需新规则时增加一个最小机制场景或状态。偏移几个像素只作为资产校准，不作为跨关卡空间方案。

## 11. 完整旅程和界面

首页突出继续/开始，现有背景与 logo 制作轻量环境场景。地图按三章花园组织，云庭独立分区，发现与进度有层级。

暂停文案明确为继续游戏、返回选关、返回主界面。子页记住来源；继续恢复进行中，回看保持隔离。设置、图鉴、纪事、重玩、存档导入/导出、失焦与恢复、手柄焦点、触摸都纳入设计。

入场短标题后收起说明。诗意文字留给发现和完成；操作信息具体。导入保留预览与确认；进行中、最好记录和完成纪念继续分开。

## 12. Web 性能与平台边界

当前以浏览器为实际入口。Web 导出基于 WebGL 2.0/Compatibility，不能按 Forward+ 特效设预算。[官方说明](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_web.html)

- 地形/碰撞按加载和状态变化更新，网格/材质稳定，避免每帧重建动态几何。
- 合并静态同材质对象；重复装饰依据剖析使用 MultiMesh；分区加载。
- 主 3D 视图为主，离屏视口仅在需要时更新。
- 透明植物、软光、水、粒子分预算，按 Compatibility/Web 实际能力提供回退。
- 控制实时光影，与原画烘焙光照匹配。
- 测量主线程、物理、绘制调用、透明叠加、内存、首载、切关和保存。
- 桌面首选稳定 60 FPS；低性能移动 Web 根据实测选择稳定档位，不能只在高端显卡测量。
- 报告硬件、系统、浏览器、导出模式和构建指纹，区分帧节奏与真正的 CPU/GPU 时间。

过去旧构建的有限性能报告不证明新方案达标。原生节点减少维护与重复计算的机会，是否更快必须实测。

## 13. 实施顺序、分工与工作量

统一目标覆盖全游戏，按可玩里程碑集成，每阶段可运行、可回滚。

| 阶段 | 交付 | 通过条件 |
|---|---|---|
| 0 基线与规范 | 可恢复基线、15 关依赖/替代解、资产/空间/输入/事务合同、目标设备 | 区分已有未提交改动，保留原可玩入口 |
| 1 完整 1-1 样板 | 原生地形、连续运动、根路操作、动作、最小 HUD、声音、保存/完成/返回 | 自主选路，上坡稳定，无逐格停顿，无墙/镜头跳变 |
| 2 差异机制 | 1-3 旋转、1-4 伙伴、2-2 携物光学；提前做 2-3/3-2 最小机制场景 | 公共合同经不同机制检验后稳定 |
| 3 全量内容 | 其余主线、三云庭、首页地图、纪事图鉴、动作音效 | 每章无口头指导试玩，公共问题回到预设修复 |
| 4 组合与收尾 | 2-3/3-2/3-3/3-4 复杂状态、所有入口/按钮、存档、设备与性能 | 规则、安全、操作、画面、全旅程一起通过 |

实施时建立独立候选和开发分支，保留当前版本；已有未提交修改先建立来源清单与可恢复快照，不能假定当前 HEAD 等于当前可玩状态。上线前移除旧手工绘制/逐格表现的运行依赖，保留规则和有价值测试，不永久维护两套正式 renderer。

并行工作流：

1. 原生世界/角色：地形、motor、平台、相机、材质。
2. 交互/UI：目标选择、种路操作、页面、输入、帮助。
3. 关卡/规则：15 关资源、依赖、事务适配、存档。
4. 素材/动作/声音/QA：艺术规格、派生动作、反馈、体验和兼容矩阵。

当前环境最多 4 个活动 agent，集成者也计入并发。避免多人同时修改同一大文件；接口、视觉定稿和最终集成有先后关系。token 增加可支持更充分的分析与验证，不能替代玩家和真实设备。

方案级工作量估算：

| 工作包 | 人日 |
|---|---:|
| 基线、设计、规范 | 2—4 |
| 原生底座与 1-1 完整样板 | 7—11 |
| 旋转/伙伴/携物/光学等机制 | 7—11 |
| 其余主线与云庭适配 | 10—16 |

## 14. 验收与完成定义

### 规则/功能

15 关主路与关键替代解通过；新移动不能绕种路、低拱或保持条件；历史成立不替代当前光水影。快点、跳过、暂停、撤销、返回与重载无双提交/幽灵通路。

存档覆盖进行中、最好记录、回看、云庭发现与旧档迁移。所有按钮验证真实导航目的，不能仅证明回调执行。

### 操作/画面

全关卡同一运动、脚点、朝向、坡道、遮挡标准。人物脚点、当前目标、合法下一落脚区不被常驻 UI 挡住。起停转向、坡道反向、斜向边缘、平台承载、携物、换手、撤销无明显穿插/漂浮/失控。

种路生长中尝试进入、角色跨边时撤回、伙伴落后、机关运动中撤销、上下重叠平台读档，都同时校验画面和规则占用。

### 屏幕/平台

布局样本覆盖 390×844、568×320、594×462、1280×720、1920×1080、2560×1440 与超宽屏，并测窗口变化、大字体、减少动态、触控、手柄、失焦恢复。

尺寸样本不替代真实手机和核显设备。无法覆盖的设备明确留项，不冒充验证。

### 人类体验

先找 5—8 位未接触项目的玩家，不口头讲解法，观察目标理解、根台发现、自主选方向、解释种路因果、错误后尝试与撤销。

建议首关目标为大多数人在约 90 秒内掌握基础移动并种出第一节路。这是待验证目标，不是当前测试结果。统计纯往返、误触、无效尝试、求助、换手、撤销及继续探索意愿。

自动化、画面对照、FPS 共同支持验收，不能替代玩家是否觉得自然和愿意继续玩。

## 15. 持续开发的判断规则

清晰度服务当前状态，隐藏性服务发现；分别建模。先统一素材和空间定义，再调曲线。先验证代表机制，再并行制作关卡。每次优化包含可回滚基线、公共规则、参数和验证记录。

最终交付应是一套统一的制作链与完整体验：玩家亲手安排一座会以动作、植物、光、水和声音回应的立体花园。
