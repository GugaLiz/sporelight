# Godot 迁移与玩法、画面保真开发计划

日期：2026-11-04。项目：Sporelight / 微光苔原。

状态：已开始实施。原版参考为 5791bbc3dd90549b4c7ea302507ead577f51dd67；当前执行进度与限制见[迁移实施记录](26-Godot迁移实施与体验打磨记录.md)。

本计划初版仅新增文档。用户随后授权实施，现已新增独立 Godot 候选，原版 localhost:4174 与原素材保留，迁移候选使用 localhost:4185。

## 1. 目标与保留边界

采用“规则等价迁移 + 现有 2D 表现复现 + 小范围体验改善”的路线。Godot 有能力承接当前玩法和图片表现；现有 PNG/JPG 与动作帧可以继续使用，Canvas、HTML/CSS 和 WebAudio 实现需要转换。实际保留程度以代表样板的规则、图像、动画和声音对照确认。

保留当前的 2D 等角视角、插画素材和离散格子谜题。真实 3D 模型、实时物理驱动移动、新谜题或全套美术重绘属于不同范围。

| 维度 | 保留目标 | 允许的独立改进 |
| --- | --- | --- |
| 核心规则 | 根芽连接、预算/回收、旋转/升降/平移、双角色、携带、光路、雨歌、显式播种、撤销 | 已知规则缺陷单列，不随移植悄悄修改 |
| 内容 | 主线 3 章 12 关、稳定物件/地块 ID、现有合法解和 56 粒收藏预算 | 教学、收藏位置、通关条件不在本次迁移中重设计 |
| 图像与风格 | 露薇、小苔灵、鼹鼠、植物、背景、地形材质、暖色纸面 UI 与主要环境效果 | 逐项讨论遮挡、空间比例、界面占位；素材重绘另列 |
| 动画与声音 | 动作帧、朝向、携带关系、转台乘客、雨水/喷泉/蝴蝶、现有合成声音特征 | 操作反馈和动画锁定范围在体验样板中单独调整 |
| 进度 | 进行中状态、最好记录、完成纪念、姓名、设置、解锁、图鉴；保留云庭原始数据 | 数据来源一致性问题按迁移规范明确处理 |
| 操作体验 | 原快捷键、格子落点、命令含义和暂停语义可追溯 | 长按移动、有限输入缓冲、安全可视区域和遮挡避让逐项试用 |

画面保留的验收目标是：形象、材质、配色、主要效果、空间关系与动作含义一致。不同渲染器的抗锯齿、纹理采样、字体和软阴影可能不同，不承诺逐像素相同；也不能仅以“用了同一张图片”宣称画面已保留。

先取得一份 Godot 原貌参考结果，再在同一代表样板上逐项比较舒适度改进。参考结果用于验收，不长期维护两套正式 HUD。

## 2. 当前基线与范围

### 2.1 事实基线

- 主线使用 src/app/garden2 下的 GardenGame、GardenWorld、GardenRenderer、场景和样式；12 关共享这条链路。
- 云庭使用 src/app/cloud 的独立模型、控制器和渲染器，3 关不随主线自动迁移。
- 实际资源根为 assets/images；vite.config.ts 将 assets 指定为 publicDir。
- 规则与解法参考：src/app/garden2/world.ts、types.ts、levels.ts，以及 tests/garden2.test.ts、garden2Solutions.ts。
- 程序绘制集中在 render.ts、landscape.ts、gardenArt.ts、pondWeather.ts、itemArt.ts，以及 game/mushroomBuddy.ts、mole.ts、creatureArt.ts。
- 角色运动参数在 game/characterMotion.ts；声音由 game/audio.ts 使用 WebAudio 合成。
- 当前历史验证基线是全项目 140 项测试，并非 140 项主线规则测试；本计划编写时未重新执行。
- 旧 game/ 模块仍提供部分元数据、资源与工具，不能在主线迁移初期整目录删除。

历史文件 docs/24-首批体验调整与验收.md 及 docs/qa-experience-20261104 属于已撤回实现，不能作为迁移目标或当前验收证据。docs/22、23 保留诊断价值；本计划是在用户考虑 Godot 后提出的新路线，不代表此前已经证明现有技术无法继续使用。

### 2.2 首批交付假设

首批为主线 12 关、必要首页/地图/设置/图鉴/纪事/结算，提供 Web 与 Windows 测试构建；复用主要素材并保留代表效果。

Windows 是规划中的首批第二平台，用于早期检验跨端路线；若实施时确定只交付 Web，可重新裁剪外围工作。Android/iOS 原生、商店发布、云同步、多人、新关卡、全套重绘另行估算。

云庭作为后续独立工作包。主线版本必须完整保留其旧存档数据，并清楚说明新构建是否已提供云庭入口；保留数据不等于云庭迁移完成。

## 3. 技术路线与组件边界

### 3.1 引擎选择

- 使用 Godot 4 稳定版与类型化 GDScript；实施 P1 时核对并锁定准确版本、导出模板和构建参数。
- 首批 Web 与 Windows 均以 Compatibility 渲染路径制作和验证，减少样板期间的渲染差异。
- 保持 2D 等角伪高度，不依赖引擎刚体或碰撞求解器判定能否走到下一格。
- JavaScriptBridge 用于 Web 外壳、旧存档导入及必要的对照试验。长期规则核移植到 GDScript，供 Web/Windows 共用。
- 主线完整 HUD 使用 Godot UI；网页外壳只承担加载、嵌入、浏览器能力和迁移入口。
- 本机自动验证使用 Godot headless 与参考回放；真实渲染、音频和窗口行为使用导出构建验证，headless 不能替代画面验收。

### 3.2 拟定结构

以下目录为实施时的建议，当前尚未创建：

    godot/
      project.godot
      contracts/                  状态、命令、结果、事件与内容版本
      core/                       规则、机制、撤销、派生世界
      content/                    关卡数据与资源清单
      application/                GameSession、输入、动画协调、场景切换
      presentation/world/         投影、地形、角色、机关、天气、遮挡
      presentation/materials/     纹理绘制和少量必要材质
      ui/                         HUD、地图、设置、纪事、图鉴和结算
      services/                   SaveRepository、AudioService、平台适配
      assets/                     从既有素材按清单同步的运行资源
      tests/                      规则、存档、场景和可视化验收入口
    tools/godot-migration/        JS 参考回放、资源同步和比较工具
    docs/qa-godot-migration/      后续基线、差异报告、录屏与验收记录

Godot 工程放在当前仓库内，旧 Web 实现保留。新工程运行资源按白名单从现有 assets 同步，注明来源与 hash；不产生两份靠人工分别维护的素材。导入缓存、导出构建和制作源图按用途治理，不把全项目图片目录全部打入发布包。

### 3.3 数据契约

| 契约 | 职责与约束 |
| --- | --- |
| LevelDefinition | 稳定地块 ID、地图、根线、机关配置、初始物品、地标与目标；旋转/平移/升降使用明确的配置类型 |
| GameSnapshot | 规则状态、版本、人物位置、物品归属、根线/机关/收藏；不包含像素位置、贴图路径、动画进度或 UI 展开状态 |
| GameCommand | 有类型的移动、互动、生长、回收、换手、携带、放置、节拍、撤销等；旧字符串命令只在适配边界解析 |
| CommandResult | accepted、changed、reason_code、before/after、领域事件和状态版本；区分失败、无变化、有效变化 |
| GameSession | 唯一可变规则实例、命令执行和会话内撤销历史；支持运行与 headless 回放 |
| PresentationPlan | 将命令结果转换为位移、姿态、轨迹、特效和声音；不修改谜题结果 |
| HudViewState | 当前目标、可用命令、资源数、角色和反馈；UI 不自行推导另一套通关规则 |
| ViewportLayout | 可用宽高、实际 HUD 占位、安全区域、输入方式和文字缩放；镜头和界面共同消费 |
| VisualAssetSpec | 稳定资源 ID、路径/hash、尺寸、alpha、锚点、显示尺度、过滤/重复、颜色与使用位置 |

规则核不依赖 Sprite、Tween、场景树或渲染帧。非撤销规则命令在相同 Snapshot、命令与内容版本下结果确定；撤销由 GameSession 的状态及历史共同决定，对照测试同步重放历史，重载后历史为空。动画快慢不改变谜题合法性。

控制器按状态版本生成一次确定结果，再执行表现与提交；取消、暂停、重来、切场景时防止重复提交。试奏等定时逻辑转为离散规则命令，视觉时钟与规则进度分离。

## 4. 图片、程序绘制与声音的迁移方案

### 4.1 保持投影和实际资源映射

初期沿用当前投影：

    screen_x = (x - z) × 35
    screen_y = (x + z) × 17.5 - h × 48

地面顶面基准为 70×35。先保持现有角色、地标和地形尺度、相机取景及脚底锚点，完成参考结果后再单独评审尺度调整。

资源清单以运行时最终 alias 为准。例如当前 ball alias 最终由 journey-gardens/buddy-ball.png 覆盖；不能只按 CHARACTER_FILES 或目录名推断实际画面。

原图先保持内容与透明边；逐类配置无损导入、过滤、纹理重复和必要 mipmap，通过比对后再考虑压缩、裁边或图集重排。当前 Canvas 的图像平滑和最高 DPR 2 策略也纳入对照。

### 4.2 逐类工作与验收

| 当前内容 | Godot 承接方式 | 验收重点 |
| --- | --- | --- |
| 露薇透明动作帧 | Sprite2D/SpriteFrames，迁移原取帧和姿态计算 | 方向、帧序、55ms 步帧、翻转、呼吸、跳跃、脚底不漂移 |
| 角色携带袋与物件 | 角色子节点、姿态锚点表与动态遮挡部件 | 走路/跳跃/滚动/伙伴状态下物品位置和归属正确 |
| 背景、植物、花床、图标 | Texture2D 与精灵/界面纹理，保留原素材 | 比例、透明边、章节色调、背景裁切、加载失败占位 |
| 地面顶面、侧壁、台阶 | Polygon2D/自定义绘制、UV、重复纹理 | 顶面和立面拆分，世界纹理相位一致，无接缝；视觉台阶不创建额外规则连接 |
| 池塘岸线与反射 | 原轮廓算法、蒙版/多边形、分层渐变和背景反射 | 保留有机岸形、水体层次、湿石与岸边接触阴影 |
| 瀑布、水流、湿地面 | 原形状公式与时间驱动的绘制或材质 | 出水点跟实际地形匹配，水位和岸高一致，暂停后恢复无跳变 |
| 小苔灵、鼹鼠、喷泉、铃铛 | 迁移程序形状；静态部分必要时烘焙，动态部件独立 | 形象、材质渐变、动作状态保持；不能用临时素材替换后宣称保真完成 |
| 蝴蝶、雨滴、涟漪与居民 | 初期复现原数学与固定视觉时钟 | 运动节奏、停驻、低动态/关闭粒子状态、暂停行为 |
| 光环、光路、引导箭头 | 自定义绘制、Line2D、软边纹理或必要 Shader | 路线正确、线宽与软光接近；视觉不影响可达性和完成判断 |
| 纸感 HUD、花纹和按钮 | Control/Container/Theme，纸纹重复与角饰分离 | 纸纹不被拉伸，花纹、阴影、颜色、中文换行、焦点和快捷键提示 |
| 合成音乐与音效 | 从当前合成参数制作音频资源，必要时保留调度逻辑 | 音色、包络、循环衔接、音量分组、暂停/恢复、首次用户手势解锁 |

代码绘制不是完整现成图片。静态结构可以烘焙，有限动作可以做图集，连续状态用实时绘制；依据效果和维护成本分别选择，并保留来源与复现参数。

### 4.3 层级与遮挡

初期复现当前稳定绘制顺序及 tie-break，再单独验证遮挡改善。Godot Y-sort 不能直接代替现有 x+z 深度规则：屏幕 Y 已包含高度偏移，直接排序可能改变前后关系。

将逻辑地面锚点与视觉高度偏移分开；明确背景、水体、地形顶面/立面、地标、道具、人物、世界特效、标签和 HUD 的层关系。跨多格平台按必要部件拆分，避免把整座庭院作为一个排序对象。

遮挡专项用例包括：大帽子遮邻格、同格伙伴、高台后人物、花门前后、转台中间态、携带物、花床与 HUD 重叠。体验改进优先采用合理布局和视觉部件避让，再比较局部淡化或轮廓提示。

### 4.4 明确的跨引擎差异

Canvas 渐变、clip、pattern、shadowBlur，CSS 多层背景、内外阴影、multiply，以及字体度量都需要复现。先以分区对照确认差异，再决定做材质、烘焙层或接受微小采样差异。

系统字体 Microsoft YaHei/SimSun 不能假设所有平台都有；实施时确认可用字体与分发条件，用字体回退、行高和断行样例核对。画面已有烘焙光照的素材保持其色彩，新增全局照明必须经过单独对照。

## 5. 规则与存档保真

### 5.1 参考回放

冻结旧 JS 规则作为对照源。从现有解法先展开真实逐格 move/act 命令，再导出每步结果、Snapshot、派生 tiles、可用命令、预算、光路、ready/together 和收藏。不能让两端各自寻路，只比较最终通关。

单独测试寻路的合法边、可达性和最短长度；多条最短路都合法时，不把任意遍历顺序当作唯一玩法要求。集合字段按语义比较，根线、乐句等顺序有意义的数据保留顺序。

专查负坐标、取模、JSON 数值、null/缺字段、字典遍历、深拷贝与引用共享。旋转后保持模块局部地块 ID；不能因屏幕位置改变而重命名人物站位。

### 5.2 机制覆盖

| 关卡 | 必须通过的代表约束 |
| --- | --- |
| 1-1 | 两方向引芽、收回重选、收藏与完成区分、显式播种 |
| 1-2 | 两条完整根路、可退死路、预算、占用根节保护、伙伴会合 |
| 1-3 | 四向转台、偏心乘客、稳定地块身份、旋转撤销 |
| 1-4 | 重杆、低拱、踏板、门闩、门铃、花门、双角色会合 |
| 2-1 | 三档水位、清露拾取/携带/消耗、浮台与岸连接、占用保护 |
| 2-2 | 位置与角度共同决定光路、携带不反射、错误放置可恢复 |
| 2-3 | 六种乐句排列、逐拍/自动播放、换手/暂停/重载、重置乘客 |
| 2-4 | 蜜花、光虫邀请、靠岸、乘客/物品运输、授粉后开放 |
| 3-1 | 提灯、低通道、灯方向、照孔、发现记录与带灯会合 |
| 3-2 | 两种留影顺序、搬走影柱后影形保留、占用影路保护 |
| 3-3 | 四种分水朝向恢复、供水、升降动力、安全下降与清露消耗 |
| 3-4 | 根/水/光/月联动、镜叶随平台移动、当前条件和双人会合 |

通用测试：失败命令不改状态/撤销历史；成功后 undo 恢复完整前态；收藏不重复且总预算 56；一物一持有者、一人一携带物；人物和物品不会因结构变化失去落脚点；完成后漫步不重开结构操作。

每个中间状态保存/恢复，覆盖坏版本、缺字段、错误位置和归属。当前撤销历史不随存档保存，首轮兼容该语义；雨歌 trial 是嵌套 JSON，重置对新增收集和观察的保留行为需专测。

已知缺陷独立登记，例如 3-2 合法替代解与提示不同步、旧成绩来源分裂。不能收窄合法解来迁就提示，也不能把已知数据问题作为“忠实迁移”静默延续；规范明确哪些规则必须等价、哪些数据修复需单独验证。

### 5.3 存档迁移

覆盖三套现有键：sporelight.save.v2、sporelight.garden2.v1、sporelight.cloud-gardens.v1；兼容清单另包含 sporelight.save.v1 读取回退。

分别保留 runs、memories、records、最后关卡、姓名、设置、解锁、图鉴和云庭记录。新主线有效记录按本关收藏预算校验后优先；旧记录仅在主线记录缺失时回退补齐。较低的重玩结果不覆盖更好的既有记录。通关记录不等于存在可回看的完成 Snapshot，不能伪造纪念状态。

更细的旧/新成绩合并、解锁派生、重复导入策略在 P0 固定示例和预期输出。运行中状态与完成纪念分开；云庭尚未迁移时保留原始原文，不把其数据解释为主线状态。

- 同浏览器/profile 且同源的 Web 页面可通过 JSBridge 读取旧 localStorage；协议、主机、端口任一变化都属于不同源。localhost:4174、127.0.0.1:4174、localhost:4185 不共享旧存档。
- 测试预览使用独立端口和测试存档。跨源及 Windows 原生统一支持由旧页面导出、再显式导入的版本化 JSON。
- Godot 的 user:// 与旧 localStorage 分别实现；Web 需验证 IndexedDB 持久化、刷新和站点存储失败，Windows 需验证退出/重开和文件写失败。
- 导入先校验、显示结果、保存备份，写入并重读成功后才标记完成；重复导入幂等，导入失败不覆盖成空新档。
- 不扫描浏览器 profile，不删除旧键，不在开发测试中读取或覆盖用户当前真实进度。

## 6. 体验改善的单独工作线

迁移参考结果先保留当前快捷键、方向含义、相机/比例和动作时长，供定位引擎差异。之后在已通过的代表样板里逐项比较：

1. 长按方向连续走格，松开后按既定格子规则停止；暂停、失焦、切场景清除持续输入。
2. 为动作结束前的方向输入设置有限缓冲；初期最多保留一次有意义的移动意图，避免释放按键后长队列继续行走。
3. E 等资源改变动作保持明确目标与执行条件；不得将试按、长按或接近目标解释为多次消耗。
4. 为有效操作提供即时可见反馈；区分“已接收等待”“当前不允许”“执行失败”。
5. 保留当前等角方向映射，先改进方向提示；任何按键语义重映射单列，避免改变已有肌肉记忆。
6. HUD 与镜头共享可视区域，先修可用空间和关键对象遮挡。角色缩放、持续跟随、教学简化各自单独比较。
7. 移动、互动、机关播放分别约定可取消范围；切场景、重来、暂停/恢复和存档不得产生半次提交。

已撤回的紧凑 HUD、角色缩小、输入模块与首关教学不直接复制进新工程。先给可试玩对照，再确定这次采用的具体参数。

## 7. 分阶段执行与验收闸门

阶段表示依赖与验收，工作包可在接口稳定后并行；下述里程碑时间均为总量子集。

| 阶段 | 交付物 | 通过门槛 |
| --- | --- | --- |
| P0 冻结基线 | 版本/内容清单、展开命令回放、存档样本、资源 manifest、截图/录屏规范、已知缺陷清单 | 来源均为当前版本；关键玩法、资产、允许变化和预期数据优先级可追溯 |
| P1 工程与契约 | 锁定 Godot/导出模板、GDScript 核心结构、投影、最小图片/UI、Web/Windows 构建 | 两端能运行；原图 alpha、过滤、脚底、纸纹与基础投影可比较；公共契约稳定 |
| P2 规则移植 | 机制核、旧命令适配、逐步对照、寻路/撤销/存档验证 | 1-1/1-3/1-4/2-2 代表机制通过，并额外通过升降/高差 fixture；随后覆盖全部 12 关 |
| P3 表现复现 | 主角/伙伴、地形、材质、天气、光路、程序造型、携带物和动画 | 山谷代表关、池塘雨水、洞穴光影均有实际画面对照；关键效果差异已处理 |
| P4 UI、音频与体验样板 | 纸面主题、中文排版、HUD、声音、输入/动画协调与单项舒适度试验 | 原貌参考达到预期；1-1/1-3 可完整试玩；1-4/2-2 关键互动有真实输入/反馈/恢复；试玩确认方向 |
| P5 全量内容与外围 | 其余关卡、首页/地图/图鉴/纪事/设置/结算、进度仓储、旧存档导入 | 全关状态闭环，界面展示一致；迁移可重复、可恢复；云庭范围明确 |
| P6 集成与交付 | 双端候选构建、完整回放/视觉/输入/存档/性能报告、回退说明 | 核心规则无未解释差异，关键对象无遮挡、无阻断问题；发布资源/存档版本对应 |

执行顺序：P0 → P1 → P2/P3/P4 的代表切片并行 → 技术门槛 → 保真与体验门槛 → P5 → P6。P2 的其余机制可继续与 P3/P4 并行，但界面和动画以已固定契约接入。

### 7.1 技术门槛

1-1 根芽、1-3 转台、1-4 双角色/携带、2-2 镜叶均通过规则与构建验证，并增加一个升降/高度 fixture。此时可以是简化画面，不代表完成最终表现。

如遇规则差异、重要效果无法复现、Web 导出关键限制，先解决该项或重新评估路线，再批量接入内容。

### 7.2 保真与体验门槛

1-1、1-3 完整试玩，1-4、2-2 关键操作实际可用，同时提供池塘水岸/雨滴、洞穴光影小样。比较原貌参考与单项改进，确认没有再次出现整体风格突变。

样板反馈属于正常产品验收，不把一次整体改动直接推广到 12 关。通过后冻结组件与交互约定，再扩展内容。

### 7.3 全量交付门槛

主线全部作者解法、替代合法状态、收藏、逐步恢复、撤销与完成后漫步通过；各章节的画面和代表动作有对照；两端保存/导入/退出重启可用。

旧版实现、旧存档和当前预览在新版本通过前保留。首次交付以单独候选构建提供，默认入口切换是后续明确的交付步骤。

## 8. 四 agent 分工与整合

| 负责人 | 独占工作区域 | 主要输出 |
| --- | --- | --- |
| 主 agent | contracts、application、主场景、project.godot、导出配置与集成构建 | 公共契约、输入/动画协调、主流程、集成报告 |
| Agent A：规则与内容 | core、content 的关卡/状态部分、规则回放与测试 | GDScript 规则、关卡定义、逐命令差异报告 |
| Agent B：场景与表现 | presentation/world、materials、视觉资产 manifest 与同步脚本 | 地形/角色/机关/环境/遮挡、图像与动画对照 |
| Agent C：UI 与服务 | ui、services、UI/存档/音频测试 | 纸面界面、菜单、进度导入、音频与设置 |

每个共享文件有唯一负责人；资源清单中关卡条目与视觉条目分文件维护。Agent A/B/C 提供独立子场景，由主 agent 组装，避免同时改动同一棵主场景。

P0 主 agent 固定接口，A 采集规则，B 采集视觉，C 采集存档/UI/声音。P1 后展开独立模块。其他 agent 在现有分支上做只读交叉复核；需要改其负责文件时显式交接所有权。

导入缓存、正式导出和最终验收由主 agent 统一执行；并行工作使用分离工作区或明确文件边界，不共享可变的编辑器缓存。各阶段小批合并并验收，不在最后一次集中整合全部模块。

并行缩短日历时间，不减少总工程工作量。样板约 10%–25%、接口稳定后的内容迁移约 25%–40% 缩短仅为规划假设；实际以首轮完成速度、构建耗时和返工量重估，不承诺按 agent 数量等比例加速。

## 9. 验证方案

### 9.1 规则与状态

- 在冻结 JS 和 Godot headless 中播放相同逐命令序列，比较结果、状态和派生世界。
- 全关合法解、上述机制边界、非法命令、撤销、收藏、恢复和错误存档。
- 规则结果不依赖动画帧率或 UI 是否打开；暂停/重来/切场景不重复提交。
- 旧全项目测试用于保护旧版及参考导出，不以“原 140 项通过”替代 Godot 规则和双端验收。

### 9.2 静态画面

主线每关至少采集入场、核心机关变化后、修复后的稳定状态；复杂关卡按机制增加样本。固定 Snapshot、视口、DPR/渲染缩放、设置、视觉时钟及资源版本。

比较同视口叠图和分区差异；地面、角色脚底、机关、光路、UI 装饰分别检查。字体和软阴影容差单独记录，不用整屏宽容差掩盖缺失地块、错位或关键遮挡。

基线几何关键锚点初始目标为同缩放下约 1–2 个逻辑像素偏差，规则地块/连接/目标身份须完全对应。此数值是 P1 校准起点；正式图像阈值由样板确认并记录，不能在批量验收时任意放宽。

当前 scripts/check-garden2.mjs 使用正确主线，但硬编码 4173 且 lowMotion=true。后续应使用明确目标地址、隔离存档和固定时钟的新基线工具。4173 属于其他项目；旧 GridWorld/#gameCanvas 脚本及已撤回截图均不作为当前主线证据。

### 9.3 动画与音频

代表动作按相同 from/to 状态和 progress=0、0.25、0.5、0.75、1 截帧；另录屏检查脚底滑移、跨格取帧、携带漂移、转台轨迹、雨水跳变、暂停与撤销。

默认动态、低动态、关闭光效、关闭粒子分别测试。音频验证首次手势、音量独立、循环衔接、暂停恢复和静音，不仅检查播放调用无错误。

### 9.4 屏幕与输入

覆盖 1280×720、1440×900、1920×1080、738×672、390×844、844×390；另检查宽度 649/650 与 900/901 两侧和短窗口、文字放大。

检查布局安全区、关键目标可见性、面板内滚动、焦点与快捷键、鼠标/触控命中、方向长按与快切、动作前后 E、失焦、暂停恢复及结算对话框。键盘是当前用户主用输入，应优先完成桌面试玩。

### 9.5 性能与资源

先记录参考设备、浏览器、分辨率、质量和预热条件，再采样帧时间、输入反馈、内存、加载与导出包体。

代表桌面目标为 60Hz 体验，初始帧耗时预算 p95 约 16.7ms；有效输入可见反馈目标 100ms 内。它们是待设备校准的目标，不能通过关闭全部现有效果或修改谜题来满足。低配/移动浏览器预算单列。

分别记录首次导入/冷加载和热运行。暂停、页面隐藏、重复进出关卡、连续重来与长时间游玩测试资源释放和状态稳定性。必要缓存/批次优化以测量为依据。

## 10. 工期、里程碑与范围调整

以下为熟悉 Godot 的开发者单人全职工程工作量参考，包含编码与相关验证；不等同于 AI 持续运行天数，也不按四 agent 直接除以四。

明确保留当前渲染效果后，程序美术、纸面 UI、合成音频与视觉对照属于已知工作，因此更新此前粗估：

| 可相加工作包 | 基础工程人日 |
| --- | ---: |
| 规则、视觉、音频与存档基线 | 2–3 |
| 工程、契约、坐标、镜头与资源基础 | 3–5 |
| 核心规则、撤销与确定性对照 | 8–11 |
| 程序美术、地形与环境效果保留 | 8–12 |
| 纸面 UI、输入反馈、中文排版与声音 | 5–8 |
| 12 关内容、必要菜单与存档接入 | 6–9 |
| 双端集成、性能、回归与修复 | 5–8 |
| 合计 | 37–56 |

相对此前 30–45 增加约 7–11 人日。再统一预留 20%–30% 风险约为 45–73 人日，即单人参照约 9–15 个工作周；不在各阶段重复计提。实际 AI 协作日历工期在样板后依据产出和返工量重估。

里程碑属于上述总量，不再相加：

- 原 3–5 人日：仅限 1-1/1-3 的简化技术试作，不能代表全部复杂机制与画面保真。
- 扩展技术门槛累计约 6–10 人日：四类代表机制、升降/高度 fixture、图片/投影及双端运行。
- 完整体验门槛累计约 14–20 人日：可试玩代表关与复杂互动、山谷/池塘/洞穴表现小样、纸面 UI、声音和单项舒适度比较。
- 全主线基础工程量约 37–56 人日；包含上述里程碑。

云庭 3 关另约 4–7 人日基础量，若要求所有云庭特有程序效果严格复现需再核对清单；Android 原生另约 5–10 人日，iOS 另约 5–10 人日且需可用工具和设备。不含商店审核。全套美术重绘单独制作清单，不随意套入迁移预算。

需重新估算的触发条件：新增平台/玩法、改为 3D、全套素材重做、复杂字体或效果无法满足目标、旧档状态与规则规范存在冲突、样板经过多轮方向性重设计。

## 11. 首个开发批次与完成定义

下一次开始实施时，第一批只完成 P0 和 P1 的最小闭环：

1. 锁定参考版本和现状，准备独立新工程位置。
2. 导出真实逐步命令、代表 Snapshot、存档样本和最终资源映射。
3. 锁定 Godot/模板版本，建立最小 GDScript 规则与投影。
4. 使用原图完成 1-1 静态场景、一个动作和纸面 UI 小样，运行 Web/Windows 导出。
5. 提供对照截图、命令差异、导入/构建结果及下一阶段风险。

第一批完成定义是“可运行、可对照、边界清楚”，不标记全关迁移或体验改善完成。计划本身不授权替换现有默认入口、重做全部美术或删除旧实现。
