# 角色动作与全关性能优化验收计划

状态：本轮已完成动作比例、全关CPU热点、普通入口、新旧连续行走、全关静态渲染及路径验收，结果与源码边界见 [62号结果记录](62-动作比例与运行性能优化结果.md)。仍有首次短暂停顿、一条未复现的934ms异常及严格像素比较未通过，均保留原始证据，不把本轮优化表述为零卡顿或所有检查全部通过。

## 目标与保护范围

本轮反馈是蹲下、播种时角色突然变大，以及 1-3 持续移动卡顿。分别检查动作原图的有效人物轮廓、脚底基准、动画缩放，以及普通入口下持续行走、机关变化和切关的实际开销。

保留已经验收的地表材质、阴影、灯光、人物清晰度和各关核心玩法。不得通过降画质掩盖问题；不得仅把首次动作的编译等待搬到加载页，或只展示暖缓存成绩。1-1 的原有玩法和已验收渲染继续作为保护基线。

## 已确认事实与待验证假设

现有 `check-normal-performance.py` 只对普通入口或显式关卡入口采集短时 idle/walking，另可触发第一次/重复生长。其 reload 模式仅保留冷启动阶段标记，冷启动的 GL/长任务详细记录会被下一页覆盖；普通模式不校验位移或动作结果。因此“采集无错误”不能证明工作负载正确执行。

`check-performance.mjs` 默认启用 QA；无 QA 时省略位移验证。其 rAF 统计不能独立证明 Godot CPU 或 GPU 的执行时间。此前约 31ms 的浏览器节奏同时出现在空白页，不能据此把游戏标作达成 60fps，也不能据此认定持续移动不存在额外停顿。

运行热路径需要计时验证的候选包括：

- `main.gd::_on_native_support_changed` 每次承载格变化执行 `refresh_world`、保存及 HUD 同步；持续走路还有每秒/停下保存。
- `native_movement.gd::tick` 跟随者可能重复求路，角色移动更新视觉；`native_garden_stage.gd::_process` 又逐帧更新角色视觉、镜头、遮挡及水表现。
- `set_motion` 已缓存前后世界与格表，但仍逐帧计算整份快照哈希、遍历表面/物件并更新表现。
- 首次绘制或首次新动作的同步 GL 调用仍可能阻塞，必须与纯逻辑 CPU 峰值分开记录。

这些是代码审阅发现的计时入口，不是已经测定的根因；不得未经证据直接删掉必要行为。

## 实施顺序

1. 固定旧版、候选版的源码摘要、构建模式、浏览器/GPU、尺寸/DPR、存档条件。保存现状动作截图与性能基线。
2. 对 idle、walk、crouch/sow、interact、jump、salute 原图计算非透明人物包围盒与脚底；检查 Sprite3D 像素比例、offset、Visual 缩放和动作帧切换，确定放大的来源。修正应保持真实姿态变化，不把蹲姿强行拉成站姿高度。
3. 普通无 QA 入口复现 1-3：连续走路、往返过格、伙伴跟随、首次转庭、重复转庭、撤销与切关。先测，再针对实际 CPU/驱动热点调整。
4. 每类机制覆盖首次与重复动作、切入与返回；冻结运行源后再做独立表现、路径及性能回归。
5. 验收通过后更新结果文档与默认预览；仍未解决的首次等待或卡顿须如实列出。

## 普通入口性能场景

使用独立 Chromium context，不读写用户现有旅程。正式主证据从首页开始，按真实菜单进入目标关；如果为诊断使用 `--level=1-3`，必须标记为显式关卡诊断，不能冒称首页流程。解锁准备如有需要单独记录，禁止在测量中调用 QA 快照、动作或每帧状态发布。

| 场景 | 执行方式 | 必查证据 |
| --- | --- | --- |
| 首次访问至首页 | 新浏览器上下文，不先暖目标页面 | 下载、100% 后阶段、遮罩消失、全程长任务与 GL 阻塞；不能保证操作系统/驱动缓存为空 |
| 首页进入游戏 | 可见入口真实操作 | 点击到可操作总等待、首帧、长任务；不要把等待挪到这里后宣称启动改善 |
| 1-3 持续移动 | 连续 20–30 秒有效路径，包含过格/转弯/伙伴跟随；重复三轮 | 实际人物位置变化的画面证据、主线程任务占用、rAF 尾部、保存相关峰值 |
| 1-3 转庭 | 首次触发、等待落稳、重复触发/撤销；至少三次 | 承载、旋转中段、落稳后的通路；分别记录每次动作峰值 |
| 切关 | 菜单进入 1-3 → 不同表现的关卡 → 返回 1-3 | 每次加载与可操作等待，材质首次出现代价、内存稳定性、角色视觉 |
| 动作首次/重复 | 第一次播种/蹲下、重复动作、切关后再做 | 站立→动作→站立轮廓连续，首次和重复耗时独立列出 |
| 缓存后重载 | 同上下文 reload 后重复同套流程 | 保留完整的第二次 trace；明确此时存档与缓存均可能不同 |

全关代表动作矩阵沿用 57 文档的实际机制，至少覆盖：1-2 生长/回收；1-3 旋转；1-4 保持重杆、伙伴穿低拱、门闩及门铃携带；2-1 水位升降；2-2 镜叶搬运、调角及光路变化；2-3 编排与执行；2-4 载虫平移、授粉生成；3-1 携灯移动、开窗与照料；3-2 搬柱、留影及日月切换；3-3 根路生长、水庭转向及花台升降；3-4 光庭转向及光束；cloud-1 旋桥取种、cloud-2 升降花台、cloud-3 伙伴守门与共同归来。此前全关路径验收可作为规则基线，本轮修改影响到的机制必须复测，不凭矩阵名称猜测实际触发。

## 指标与判定

- 每阶段报告 rAF 中位数、P95/P99/max、超过 33.4/50/100ms 的次数；连续全程采样，并包含跨阶段边界的长帧。
- CDP `TaskDuration`、`ScriptDuration`、布局增量用于主线程占用分析。它们不等于隔离的 Godot 函数 CPU 或 GPU 时间。
- Long Task 列出发生时间与持续时长，按输入标记归属。同步 WebGL 包装器仅在另一次诊断采样启用，记录 compile/link/query/upload 等阻塞；它会增加开销，不能与未包装的最终预算混合。
- 截图在测量窗口外获取，避免截图本身污染持续行走指标。动作中段的外观证据另一次专门采集。
- 普通帧预算受主机空白页节奏影响：同配置建立基线，比较新增主线程开销与长尾；不以空白页限制免除游戏自身长任务。
- 最终要同时报告首次与重复阶段、旧版与新版、各次样本。首次性能未通过则不能只用热缓存平均数宣称解决。
- 工作负载必须人工核验：真实按键成功派发不等于人物走了路、机关转动了或切关成功。未完成画面/逻辑复核时结果只能称采集完成。

## 新工具与证据位置

新增 `tools/godot-migration/check-action-performance.py`，不改动总代理正在使用的 `check-normal-performance.py`。通过 JSON 场景指定有名称的阶段和真实按键/点击/等待，保存逐阶段前后截图、输入时间戳、主线程增量、rAF、长任务、可选 GL 同步调用，以及首次/重载两套完整原始记录。工具不会自动把采集成功标记为性能或玩法通过。

示例命令（场景需按已验证的真实菜单和路径编写，不能直接复制坐标跨尺寸使用）：

```powershell
C:/Python314/python.exe tools/godot-migration/check-action-performance.py --base http://localhost:4222/ --scenario path/to/verified-scenario.json --output docs/qa-godot-native/action-performance/baseline
```

诊断时额外使用 `--gl-profile`；缓存重载对照使用 `--reload-once`；`--level 1-3` 仅用于明确标记的诊断入口。最终场景、源码摘要、数据和人工验收结论待测量完成后填写，不预填“通过”。

## 首轮诊断基线

`qa-godot-native/full-performance/action-baseline-1-3/` 记录旧版 `5411b226…` 的显式 1-3 入口、三轮约30秒真实行走与转庭。实际行走和转庭已复看截图；三轮主线程任务占用约59.5%/57.6%/58.4%，相对初态静止39.3%增加，后两轮仍有50–65ms长任务。此轮可能与其他 headless CPU 测试重叠，不作为最终隔离对照。

第一次撤销后仍是同朝向，说明场景不能假设单次撤销必然回到上一转庭朝向。后续场景改为四次旋转回原态再复测相同转庭，撤销单独观察。完整限制、图片和原始场景见该目录 `review.md` 与 `checks.json`；目前不据此宣称运行优化完成。
